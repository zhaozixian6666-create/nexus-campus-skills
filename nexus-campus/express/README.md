# express/ · 表达层

> 这一层不判断"该不该做"，只管"怎么把它说出来、写出来、讲出来"。
>
> 六份，2334 行。每份都是"能立刻上手改稿"的工具，不是写作理论。

---

## 一、为什么单独建一层

方法层（`method/`）解决"想清楚"，能力层（`capabilities/`）解决"判断对"。**但想清楚、判断对，说出来听不懂，一样白搭。**

真实场景：

> 一个学生项目做得不错，BP 写得像流水账，答辩讲得像念稿，最后没进省赛。
> **问题不在项目，在表达。**

**表达层的定位**：**方法的放大器。** 内容是 1，表达是 0——没有 1 是零，但只有 1 也是 1，有了表达能变成 10。

## 二、六份的分工

| 编号 | 名称 | 处理对象 | 一句话 |
|---|---|---|---|
| **写清楚** | 写清楚 | 句子 | 结论先行、一段一任务、抽象词落地 |
| **结构与开场** | 结构与开场 | 骨架 | 一个主张、按听众问题排序、时长分配 |
| **讲进去** | 讲进去 | 口头 | 听众只带走一样、具体、数字参照系、关键句三次 |
| **文档与报告** | 文档与报告 | 六种文体 | 方法可复现、数据可检验、主动写局限 |
| **风险与边界** | 风险与边界 | 发布前 | 概率×后果、书面更高危、AI 三条线 |
| **拆解与吸收** | 拆解与吸收 | 别人的作品 | 决策点、三层拆、拆三个、迁移测试 |

### 调用顺序

```
拆解与吸收 拆别人的（学）
   ↓
结构与开场 排结构 → 写清楚 写句子 → 文档与报告 按文体补要求
   ↓
讲进去 讲（如果是口头）→ 风险与边界 过风险
```

**注意拆解与吸收在最前面**：它看起来是"学"，实际是"写/讲"的前置——**不拆过好的，你不知道好的长什么样。**

### 一条硬边界

**写清楚-文档与报告只管"怎么说"，不管"说得对不对"。**

内容对错去 `../method/01_命题审查.md`（这句话站得住吗）和 `capabilities/`（这个领域该怎么办）。

**这条边界很重要**：它防止"把错的东西说得很漂亮"——那比说得难听更危险。

## 三、六份各自最狠的那一条

| 模块 | 最狠的判断 |
|---|---|
| **写清楚** | **情绪铺垫是成本的转移。** 你用三句"随着……的发展"进入正题，读者就用三句的时间等你 |
| **结构与开场** | **核心被稀释是最常见的失败。** 说得出三个主张 = 没有主张 |
| **讲进去** | **听众只带走一样东西。** 不是你希望他记住三样，是他只能记住一样，你得选 |
| **文档与报告** | **删掉所有"我做了 X"，剩下的还有价值吗？** 没有 = 这是日志，不是报告 |
| **风险与边界** | **风险 = 概率 × 后果，先看后果。** 承担不起的，不管概率多低都不做 |
| **拆解与吸收** | **拆到决策点，不是结果。** "他这个标题好"不能复用，"他为什么选这种标题"才能 |

## 四、九节结构（与方法层一致）

每份都是：解决什么 / 核心判断 / 操作流程 / 场景实例 / **反例与边界** / 常见误用 / 和其他模块的关系 / 自检 / 来源与定位

**第五节（反例与边界）在这一层尤其重要**，因为表达技巧最容易被用歪：

- 写清楚的边界：不能为了简洁牺牲准确
- 结构与开场的边界：有些场合必须按固定格式
- 讲进去的边界：**正式学术报告不要用这套**（会显得不专业）
- 文档与报告的边界：**数据不能修饰**（学术底线）
- 风险与边界的边界：**过度谨慎会让你四年没存在感**
- 拆解与吸收的边界：**不能拆成拼装工**

## 五、归属声明

**这六个模块讲的是方法，对外说「这是我的判断」。**

它们的来源是三类公开东西：

- **公开的写作与表达理论**（结论先行、信息层级、听众注意力的有限性）
- **公认的修辞与说服研究**（具体优于抽象、参照系效应、重复的强化作用）
- **对大学场景的观察**（答辩、汇报、申报书、面试这些场合到底怎么打分）

**这一层是团队的方法判断。**

这一层讲的是方法，不是个人经历。引用时说「这是我的判断」；**不要说「书上有」「研究证明」**，除非能指出具体出处和页码。

## 六、什么时候该加第七个

门槛和方法层一致，三条全过才加：

1. 现有六个覆盖不了（不是"稍微不一样"）
2. 大学场景高频（一个月触发十次以上）
3. 有明确的判定标准

候选（暂不建）：

| 候选 | 为什么先不建 |
|---|---|
| 图表制作 | 属于文档与报告的一个子项，且工具性太强（软件操作），不适合做成判断模块 |
| 邮件与沟通礼仪 | 写清楚已覆盖"写清楚"，礼仪部分散在协作与求助 |
| 笔记方法 | 属知识库自建 |
| 学术引用格式 | 是规范，不是判断。放文档与报告的格式部分即可 |
